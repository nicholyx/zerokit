# 深读：安全边界


> **本篇解决什么**：zerokit 的四道防线——风险三档、MCP 授权、供应链快照、沙箱声明——各自的威胁模型是什么、能挡什么、明确不挡什么。
> **读完能做什么**：判断「这个动作用什么 risk」「要不要给 AI 授权」「装第三方插件前该查什么」；不被「有沙箱」三个字误导。
> **前置阅读**：[design](design.md) 的「安全：三个不能省的判断」。运行时细节看 [runtime](runtime.md)。

这份文档的价值一半在「**不挡什么**」——安全承诺写满容易，写准难。

## 第一道：风险三档与确认策略

每个动作必须声明 `risk`，缺了清单都加载不了：

| 档位 | 语义 | CLI 行为 | 启动器 |
|---|---|---|---|
| `read` | 不改任何状态 | 直接跑 | 直接跑 |
| `mutate` | 有副作用但可逆 | 确认（回车/输 y） | 确认弹层 |
| `destructive` | 不可逆（删数据/发出去） | **输入动作名**复述确认 | 双重确认弹层 |

**为什么是三档不是五档**：档位越多作者越容易选错。三档对应「无副作用/可逆/
不可逆」这个用户真正关心的三分法；「会不会联网」「快不快」是**描述**不是风险，
放 keywords 和 description 里。

**为什么宁可高报**：`read` 声明成 `mutate` 只是多一次确认（烦一点）；
`destructive` 声明成 `mutate` 是用户没意识到不可逆就执行了。不对称的代价
决定了校验方向——lint 对「描述里有删除/清空字样却声明 read」的动作为告警。

## 第二道：MCP 授权（annotations 不可信）

MCP 规范明确要求客户端把工具 `annotations`（readOnlyHint 等）当**不可信数据**。
所以 zerokit 不指望 AI 客户端替用户把关，安全边界留在运行器这侧：

- `read` 动作默认放行
- `mutate` / `destructive` 必须用户在终端显式 `zkit mcp allow <插件.动作>`
- 授权带 TTL（默认 30 天，可 `--ttl 1h` 起步 / `permanent`），`revoke` 随时撤
- 被拒的调用写 deny 审计（不是静默丢弃——用户能看到 AI 试图干什么）

**为什么 allow 是命令行动作而不是 MCP 内确认**：MCP 会话里弹的确认框，
确认者是 AI 客户端的 UI，不是终端前的用户——授权链路上多一个不可信环节。
让授权只发生在用户自己的终端里，链路最短。

## 第三道：供应链（装时快照）

`plugin pack` 打包时写 `.zk-integrity.json`（每个文件的 sha256）；安装时快照
随插件落盘，`zkit plugin verify` 随时复验。篡改（改文件/删文件/加文件）都会
被列出。doctor 把「有快照但验不过」的插件标红。

**为什么不做签名**：签名解决「发布者身份」，快照解决「装完之后没被人动过」。
单机工具的现实威胁是后者——脚本被其它工具改写、同步盘冲突拼接。发布者身份
靠 GitHub 仓库与 market.json 登记表的指向，够用且不需要密钥管理。

**明确不挡**：装进来之前插件本身就是恶意的。快照只保证「装的和打包的一致」，
不保证「打包的是好的」——所以集市登记表（market.json）是人工维护的白名单，
`market add` 新源时 lint 预检。第三方依赖（node 模块/pip 包）**不代装、
绝不执行安装脚本**，缺了就报告让用户自己装。

## 第四道：沙箱声明（能/不能）

`sandbox = true`（目录钉死）、`max_output`（输出字节上限）、`env_pass`
（环境变量白名单）三个清单键（`src/core/manifest.ts` / `runner.ts`）：

| 声明 | 能 | 不能 |
|---|---|---|
| `sandbox` | 把 cwd 钉死在插件目录，声明的 `cwd` 失效 | 不隔离文件系统——插件仍可读写用户有权限的一切路径 |
| `max_output` | 超限杀进程（不是截断） | 不限内存、不限 CPU |
| `env_pass` | 白名单外的环境变量不可见 | 不隔离网络 |

**为什么不做网络断供/文件系统隔离**：声明式清单承诺不了 OS 级隔离——真要做
需要容器或沙箱框架，那是部署复杂度的一次跃迁，与「npm install 即用」的项目
承诺冲突。宁可不给假安全感：文档写清「沙箱是资源约定，不是隔离边界」，
需要硬隔离的场景请用户自己套容器。

## 密钥的诚实说明

设置项（`[[setting]]`）里的 secret 存 `~/.zerokit/settings/<id>.json`，
**明文、0600**，不加密、不进系统钥匙串。展示与日志只回掩码，CLI 读真值要
显式 `--reveal`。

**为什么不进钥匙串**：钥匙串 API 是平台绑定的（macOS Keychain / Windows
Credential Manager / Linux 五花八门），引入它等于给内核加一坨平台代码换一个
「锁的是用户自己能解锁的东西」的锁——安全边界仍然是操作系统账号。明文 + 0600
+ 文档写明，比假装加密诚实。换机器请整体搬 `~/.zerokit/` 或重新填。

## lint 是声明的守门员

`zkit plugin lint` 十二级体检里与安全直接相关的：risk 缺失/拼错（L 级错误，
加载都过不了）、secret 参数进了示例值、sandbox 动作的 env 里出现 token/secret
键名（该走 `[[setting]]`）、描述含删除/清空字样却声明 `read`（风险低报告）。
每条告警带「怎么改」指引（第一百四十四轮起）。

**为什么 lint 放在加载之前**：声明错了最便宜的纠正时机是作者手里，最贵的
时机是用户机器上跑出事故之后。把校验前推到开发循环里，防线就不用等到
运行时才生效。

## 可观测也是防线的一部分


deny 审计（AI 试图调未授权动作）、`logs --failed`（带诊断建议）、MCP 健康徽标
（成功率随审计流更新）——安全不是只有「挡住」，还有「事后看得见」。被挡的
调用写审计而不是静默丢弃，用户回头能看到 AI 当时的意图，这本身就是威慑。

**为什么 deny 不静默**：静默丢弃让攻击者（被误导的 AI 也算）以为没被发现，
会一直试。留下记录，用户能在下一次 `zkit logs` 里看到完整尝试序列。

## 四道防线合起来


```
安装时：market 登记表人工白名单 + market lint 预检 + 装时快照
加载时：risk 必须声明（缺了不加载）+ lint 十二级体检
执行时：三档确认策略 + run 数组参数级展开（防注入）
给 AI 时：annotations 不可信 → 显式 allow + TTL + deny 审计
```

没有一道是「绝对安全」的承诺，每一道都在自己的威胁模型里把攻击成本抬高
一个数量级。剩下的风险（用户自己装了恶意插件、OS 账号被打穿）写在
[已知差距](../reference/overview.md#四已知差距诚实清单) 里，不藏在营销话术后面。

---
> 这份清单不会随功能膨胀自动变长——每加一道防线，先在 [design](design.md) 里
