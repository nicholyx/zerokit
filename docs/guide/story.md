# zerokit 的故事

> 写在第 200 轮迭代之际。给新来的用户、贡献者，也给未来的自己。

## 为什么做这个

启动器很多，插件系统也很多，但它们几乎都长成两个样子：要么是闭源的商业产品（数据在别人的云上），要么是极客玩具（配置学习成本比写代码还高）。

zerokit 想做的是第三种：**一份清单，四个面**。你写一份 `plugin.toml`，它就同时成为 CLI 命令、启动器条目、MCP 工具（给 AI 用）、桌面壳动作。没有构建步骤——`node src/cli.ts` 直接跑源码；数据全在 `~/.zerokit/`——删掉即完全重置。

## 三个关键决策（回头看都对）

1. **没有构建步骤**。`node src/cli.ts` 直接跑 TS 源码（Node ≥22.18 原生类型擦除）。这个决策在 198 轮里被反复验证：改完即生效、调试即所见、CI 无编译缓存问题。代价是性能上限，但 CLI 冷启动 99ms，远在预算内。

2. **数据目录可抛弃**。一切运行数据在 `~/.zerokit/`。这意味着「卸载」是诚实的——`rm -rf ~/.zerokit` 就是真的干净。也让测试可以完全隔离（每个测试用临时 ZEROKIT_HOME）。

3. **MCP annotations 不可信**。AI 客户端（Cline/Claude）通过 MCP 调用动作时，服务端不信任客户端声明——有副作用的动作必须用户显式授权。安全边界留在运行器这侧。

## 走过的弯路（也是护栏的来源）

- **Windows 三平台 CI**：第一次跑就有 3 个平台性失败。此后「任何平台的失败都要当回事」成为铁律，后来又沉淀出十条军规（os.tmpdir/pathToFileURL/失败注入…）。
- **CHANGELOG 归档三次吞条目**：占位行守卫恒假、空壳头残留、分支切换覆盖——三次同款事故后才有了「占位行替换法 + 空头检查 + 提交前核对」三道判据，并全部机器化进 release-prep/guard146。
- **tag 打错提交**：网络故障吞掉 git fetch、本地没有 release merge 对象还打 tag——release.yml 按设计拒绝（CHANGELOG 无版本段）。此后「tag 前用 gh api 拿远端 sha + cat-file 确认」成为判据。

这些弯路没有白走：它们全变成了护栏（guard146 / release-prep 三重自检 / contrast-audit / i18n-scan / a11y-scan / cli-copy-audit / mcp-copy-audit）。**人（和 AI）会犯错，护栏负责兜底**——这是本项目最大的元教训。

## 数据总览（v2.1.0 时点）

见 [v2 基线指标快照](../reference/baseline-v2.md)（脚本生成，随 minor 刷新）：CLI 冷启动 99ms、130 个测试文件 3054 项断言、13 个内置插件 52 个动作、四审计护栏全绿。

## v2 线的未来路线

- **插件生态**：集市审查机制、社区插件签名
- **协作**：多用户配置档、团队动作集（bundle 已有雏形）
- **AI 协作面深化**：MCP 资源订阅、动作链的 AI 编排
- **移动端**：清单派生的第五个面（探索中）
- 不做清单：云端同步（违背本地优先）、账户体系（违背可抛弃）、遥测（违背隐私底线）

1. 读 [START-HERE](../../START-HERE.md) 跑起来（5 分钟）
