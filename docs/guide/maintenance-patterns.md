# 维护模式判据（v3 线沉淀，第二百四十轮立）

> v3 线 39 轮（201-239）跑出三类维护轮型。本文沉淀共性判据——
> 「下一轮该做什么」的选型参考，也是评估一轮价值的标尺。

## 三类轮型

### A. 功能轮（约 60%）
新能力落地（如 216 services 面板、220 全景总检、227 JSON 契约）。
判据：**十项验收里至少 6 项是「新增可验证行为」**；lint 八审计全过；
断言净增。

### B. 盘点确认+锁定轮（约 25%，232/237/238 三轮定型）
功能在历史轮次已有、断言未锁——跨轮演化随时可能回归。
判据：**盘点结论写进 issue；既有接线用断言锁定（防回归是真交付）；
零或极少新增运行时代码**。价值不在「新」而在「确认正确 + 锁死」。

### C. 事故修复轮（约 15%，223/233）
护栏抓到真问题（计数漂移/npmmirror/squash 丢提交）。
判据：**修复与判据同轮落盘**（issue 验收记录 + CHANGELOG）；
判据要可执行（「跑 X 命令」优于「注意 Y」）。

## 选型启发

1. 提出主题前先 grep 盘点——若是 B 型，验收项就该是「锁定」而非「新做」。
2. 修复走完不落判据 = 没修（下次同坑必踩）。
3. A 型轮的价值密度 = 新行为 × 可验证性；纯 UI 无断言的改动最脆弱。

## 断言数回归护栏（第 271 轮，2026-11-12）

**事故**（270 轮）：整块重写吞掉既有子命令分支，test-all「全绿」但断言数 3191→3157（-34）——条件断言静默跳过不会 fail，sync-counts 还把文档同步到低值，无一处报警。

**护栏**（三层）：

1. `scripts/assertion-baseline.json` 入库——当前断言数基线。
2. `test-all` 末尾守卫：总数 < 基线且全绿 → exit 1 + 事故型提示（指认结构丢失）。
3. `sync-counts`：计数上升自动抬基线；下降不自动（提示须 `--force`）。

**判据**：

- 改子命令分发区/大块重构前，`git show HEAD` 全量读既有 case。
- 「全绿但计数降」= 结构性丢失——立即 stash 对照基线。
- 删测试是有意动作：显式 `--force` 降基线，不静默。
