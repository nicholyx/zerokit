# 深读：插件运行时


> **本篇解决什么**：动作真正执行的那 0.5 秒里发生了什么——进程怎么拉起、编码怎么统一、常驻宿主为什么能把 476ms 压到 22ms、超时和输出上限在哪一层拦。
> **读完能做什么**：写插件时预判性能特征（什么时候值得声明 `runtime = "host"`）；排查「跑不出来」类问题时知道去哪一层看。
> **前置阅读**：[design](design.md)（清单派生四个面的总纲）。参数怎么声明看 [plugin-spec](../reference/plugin-spec.md)。

## 进程模型：一条动作的生命周期

```
plugin.toml 声明 run = ["{python}", "proxy.py", "status"]
        │
        ▼
buildVars 展开占位符（{python}/{node}/{input}/{setting.*}）
        │
        ▼
执行路径按快慢选：常驻宿主 → 子进程（没有 worker 中间层）
        │
        ▼
stdout 按声明解析（output="json" 解析 / 原样文本）
        │
        ▼
审计落一行（成功/失败/耗时/参数掩码）
```

**为什么没有 worker 线程层**：早期版本试过「宿主 → worker → 子进程」三级降级，
实测 worker 层在一次性的 CLI 调用里纯属开销——Node 起 worker 的成本和起子进程
几乎一样，还多一层通信序列化。删掉后没人怀念它。降级链只剩两级：常驻宿主失败
就退回直接 spawn，行为差异只是快慢。

## 占位符展开

`run` 数组里的 `{xxx}` 在执行前展开（`src/core/runner.ts` 的 `buildVars`）：

| 占位符 | 展开为 | 说明 |
|---|---|---|
| `{python}` / `{node}` | 实际解释器路径 | 跨平台：Windows 跳过微软商店假 python、macOS 认 brew 装的 |
| `{input}` 等参数名 | 用户填的值 | 只替换**声明过的**参数，防注入 |
| `{setting.xxx}` | 设置项值 | secret 项同样展开，但审计里只记掩码 |
| `{result.data.字段}` | 上一步结果 | 只在 chain 组合动作里有效 |

**为什么不做成 shell 字符串模板**：`run` 是数组不是字符串，占位符替换发生在
参数级——`{input}` 传 `"a; rm -rf /"` 时它永远是**一个参数**，不会被 shell 拆开。
这是清单格式里最便宜也最硬的一条注入防线（`shell = true` 显式声明才放开，
此时作者自己负责）。

## 编码：统一 UTF-8，例外要声明

内核给每个子进程注入 `PYTHONIOENCODING=utf-8`（`src/core/runner.ts`），
Python 子进程的 stdout/stderr 按 UTF-8 解码。Windows 上 PowerShell 输出
GBK 的老插件，在清单里声明 `encoding = "gbk"`，内核按声明解码。

**为什么不自动探测编码**：探测是猜，猜错是乱码。显式声明一次，永远正确——
这和「风险要声明」是同一个哲学：宁可让作者多写一行，不给运行时留模糊地带。

## 常驻宿主：476ms → 22ms 的原理

一次性执行一个 Python 动作的耗时构成：解释器冷启动 ~300ms + `import` 一次
~150ms + 真正的活 ~25ms。`runtime = "host"` 的插件在**长生命周期进程**
（启动器、MCP 服务端）里走常驻宿主：解释器起一次、import 做一次，之后每次
执行只付「真正的活」那部分。

**为什么一次性 CLI 调用不走宿主**（`src/core/runner.ts` 里 `worthHosting`
一行）：宿主冷启动要 1.6 秒（起解释器+预热 import），`zkit run` 每次都是新
进程、宿主用完即弃——单次调用走宿主反而比直接 spawn（~0.5 秒）慢三倍。
这是实测踩出来的回归：曾有一版无脑全走宿主，CLI 用户集体变慢。

| 场景 | 走哪条路 | 首次 | 后续每次 |
|---|---|---|---|
| 启动器/MCP 里跑 host 插件 | 常驻宿主 | ~1.6s（一次性） | ~22ms |
| `zkit run`（任何插件） | 直接子进程 | ~500ms | 同样 ~500ms |

## 超时与输出上限：两层硬顶

- **时间**：动作声明 `timeout`（秒），默认 60。超时 SIGKILL，`ExecOutcome`
  标 `timeout`。执行中用户按停止（`/api/stop`、Ctrl+.）走同一条 abort 通道，
  标 `stopped`。
- **输出**：全局硬顶 1 MiB（`MAX_OUTPUT`）——超出部分**落盘**到
  `~/.zerokit/data/artifacts/` 并返回路径，不静默丢弃；声明 `max_output`
  （如 `"2KB"`）的动作超限时直接杀进程——半截 JSON 比失败更危险，
  宁可整段报错。

**为什么全局上限落盘、声明上限杀进程**：全局上限面对的是「意外的大」
（谁都需要那份数据，给路径）；声明上限面对的是「作者知道多大算异常」
（超过就是插件坏了，截断只会掩盖）。

## 组合动作（chain）的编排

`type = "chain"` 的动作没有自己的进程：步骤依次执行上一步的真实动作，
`{first.data.字段}` 占位符从上一步的解析结果取值，`risk` 取所有步骤的
最高档（fail-closed）。任一步失败整链失败，已执行的步骤效果不回滚——
所以破坏性步骤应该排最后。

**为什么不在失败后回滚**：回滚需要逆操作，而「逆操作安全」无法从清单推断
（写文件可以删，发邮件撤不回）。诚实的语义是「链是顺序执行，不是事务」。

## 常驻服务（service）

`[[service]]` 声明的动作（start/stop）通过 `--detach` 拉起守护进程：内核
记住 pid，stop 时按 pid 杀。服务进程**不随内核退出**——启动器关了，
代理还在跑，这是功能不是泄漏。孤儿检测（doctor）会报告「声明了 stop 动作
但进程不在」的服务。

## 每次执行都落审计

`~/.zerokit/logs/audit.log` 每行一条 JSON：时间、插件、动作、调用方（cli/mcp/ui/深链）、
成功与否、耗时毫秒、参数（secret 全程掩码）。这不是调试日志——是产品功能：
启动器的执行历史、最近活动面板、失败诊断建议、MCP 健康徽标全部从审计流读。

**为什么审计是 JSONL 不是自由文本**：消费者全是程序。人看的呈现（相对时间、
分组、徽标）在渲染层做，存储层保持机读——同一份数据喂四个面。

## 排错入口


| 症状 | 看哪 |
|---|---|
| 动作跑不出来/编码乱码 | 清单 `encoding` 声明；`zkit plugin lint` |
| 间歇性慢 | 是不是 CLI 单次调用跑 host 插件（预期行为，见上表） |
| 输出被截 | `~/.zerokit/data/artifacts/` 里找完整版 |
| 疑似注入 | `run` 数组展开是参数级的，查是不是声明了 `shell = true` |
| 进程杀不死 | timeout 走 SIGKILL；服务类看 stop 动作与 doctor 孤儿检测 |
