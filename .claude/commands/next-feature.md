继续开发新功能。你作为该开源项目的**维护者**，必须想象这个项目要如何打造才能吸引更多的人来使用。

如果本命令后附带参数（$ARGUMENTS），本轮就围绕该主题展开；否则自行选题。

## 动手前（务必按顺序）

1. **先同步最新代码**，确保基于最新 `main` 开工（`git switch main && git pull --ff-only`）。
2. 了解近期做过的功能，避免重复造轮子、寻找演进方向：
   - 开着的 Issue（`gh issue list`）——有明确待办的优先挑（如平台债、文档缺口）
   - 最近的 PR（`gh pr list --state merged --limit 10`）与开着的 PR（`gh pr list`）
   - 最近的 commit（`git log --oneline -15`）
   - `docs/overview.md` 的「待办 / 已知差距」——项目层面的诚实账本

## 本轮目标

- **四个面必须一致受益**：zerokit 的核心卖点是「一份 plugin.toml 同时派生
  CLI / MCP / 启动器 / AI 工作台」。新能力要问一句：哪几个面能用上？
  只惠及一个面的设计，先想想是不是姿势不对。
- **敢于创新**：做出有特色、有想象力并且与众不同的功能。
- 可自行检索同类项目（uTools / Raycast / bleak 等），对比跟我们的差异，
  把优秀的内容吸收过来——但**不能一味复制**，要经过融合改造，
  无缝融入本项目。
- 优先做「让接插件这件事更容易」的改进：插件是生态，生态靠的是
  写插件的门槛足够低。

## 硬性要求

- **测试全部补齐**：`node scripts/test-all.mjs` 全绿（不联网、不花钱）；
  新功能配新断言，放在 `test/` 下按现有风格写。
  注意 mcp-smoke 是自包含的（临时 ZEROKIT_HOME），新测试同样
  **不得依赖本机已装的插件或数据目录**。
- 确保新加的每一个功能都**不影���老功能**（回归测试必须全绿；
  macOS/Linux 上有 3 个已知平台性失败，见 Issue，其余失败必须当回事）。
- **界面改动要真实打开验证**：`node src/cli.ts ui --open` 起界面
  人工过一遍交互，别只看测试绿。
- **走完整 GitHub 流程**：Issue → 聚焦分支 → 约定式提交 → PR →
  CI 绿 → squash merge → Issue 自动关闭。用户可见的变更往
  `CHANGELOG.md` 的 `Unreleased` 段补一条。
